# 用户现场报告分诊记录（2026-10-24）

两条来自已安装用户（6.17 产品线）的 bug 报告及其证据链分诊。结论均基于仓库
只读核查，未接设备；两项都向下兼容到正在进行的 7.0 移植（见各节末尾）。

## 一、安装后自动重启到 fastboot

### 机制

1. 安装收尾 `tools/install-liuqin.py:669-670` 只做 `fastboot --set-active` +
   `reboot`：置槽 `active=1`、`priority=3`，但 **`successful=0`、
   `tries_remaining=7`**。安装器从不标记槽成功。
2. 标记**唯一**发生在首次启动的 initramfs（`initramfs/init:1234-1258`）：
   persistent 模式 + UFS 证只读 + 持久根探针成功 + cmdline 有
   `androidboot.slot_suffix` + `/bin/liuqin-mark-slot-successful --mark` 的
   全部 fail-closed 校验通过，才写 GPT。任何一道不过 → 不标记、不交接。
3. 槽未标记时 ABL 每次启动扣一次重试，7 次后置 unbootable 并回退另一槽；
   **两槽都不可启动时 ABL 把设备停进 fastboot**（init:1243-1244 的注释
   明写这一点）。

### 关键判别：报告者是系统性首启失败，与布局无关

- linux-only 只写 `boot_b`、A 槽留原厂（`docs/INSTALL-TESTING.zh-CN.md:155-156`），
  但默认 `--android-size 0` 会**删除 userdata**：A 槽的 Android 已起不来，
  slot-B 系统性失败时没有真正的回退。
- dual 布局两槽同一镜像：A 耗尽 7 次 → 回退 B（同一镜像、同样失败）→ fastboot。
- 两种默认布局的系统性首启失败最后都指向 fastboot（或起不来的 Android
  反复重启），因此"自动重启到 fastboot"指向**系统性首启失败**（持久根探针
  被拒或 `--mark` 被拒）而非随机崩溃，不用先猜布局。

### `--mark` 被拒的头部嫌疑：容量变体

`device/boot/liuqin-mark-slot-successful.c:31-40` 把 `/dev/sde` 钉死为
2923429888 字节、boot_a/boot_b 钉死在固定扇区（75014-124165 /
344107-393258）。 只有 256 GB 布局真机验证过；若 /dev/sde 的几何随容量
SKU 变化，其他容量机型每次首启都标记失败，约 14 次重试后必落 fastboot。

历史同源修复：`7470303`（安装器把 boot 镜像零填充刷满分区，消除残留的
旧 Android AVB footer 致 ABL 校验失败）。已在 main；旧版安装器用户先判
版本。

### 诊断清单（给报告用户）

1. `fastboot getvar all`：`current-slot`、`slot-retry-count:a/:b`、
   `slot-successful:a/:b`、`slot-unbootable:a/:b`、`unlocked`、电量。
   两槽 retry≈0 或 unbootable=yes ⇒ 重试耗尽机制确认。
2. 数进 fastboot 前的自动重启次数（约 7/槽）：区分"镜像一点都没启动"与
   "启动了但标记失败"。
3. 重新 `fastboot boot installer.img` 后 telnet 192.168.7.2:2323 跑：
   `cat /proc/cmdline`（slot_suffix、`androidboot.mode`）、
   `blockdev --getsize64 /dev/sde`、`/bin/liuqin-mark-slot-successful --check a`
   与 `--check b`、`findfs LABEL=LIUQIN_ROOT`、`dmesg | grep -i ufs`。
4. 面板照片：initramfs 日志直打面板，关键行（init:1247/1252/1256 等）可
   分辨是哪道门拒绝；7.0 板级 DTS 无 pstore，重启后内核日志不可恢复。
5. 确认安装器版本与布局（dual / linux-only）。

### 修复候选（未实施，仅记录）

安装器侧在最终 reboot 前标记成功（需放开 C 工具对非运行槽的拒绝，中
风险）；解耦标记与交接 / systemd 补标记（运行系统写 sde 曾被刻意退役，
中高风险）；文档补"槽成功/重试计数模型"与卡 fastboot 的修复食谱
（`fastboot --set-active` 可把 tries 复位为 7，低风险高价值）；电量门
程序化；容量变体改为从 GPT 动态解析 boot 扇区（保持 CRC fail-closed
契约，需第二台真机验证，中风险）。

### 对 7.0 移植的影响

- 我们计划的首装是 `--layout linux-only`，目标即整机 ARM PC：默认
  `--android-size 0` 全盘归 Ubuntu、不保留 Android（128 GB 本就紧张，
  应急 Android 与项目目标相悖）。该默认会**删除 userdata**
  （`INSTALL-TESTING.zh-CN.md:28`），A 槽失去可启动的 Android——
  slot-B 首启若系统性失败，**无在机回退，落点是 fastboot**。容错路径是
  `fastboot boot installer.img` 重装（RAM 安装器完好、telnet 可诊断），
  因此 bug-1 机制对首装的影响前移为**前置门**：首测 RAM 阶段的
  `blockdev --getsize64 /dev/sde`（容量变体闭环）与本分诊清单是首装前
  必须做完的检查，不是可选项。
- 我们的平板是 128 GB：首测 RAM 阶段加一条 `blockdev --getsize64 /dev/sde`
  （等于 2923429888 ⇒ 该 LUN 跨 SKU 一致，首装标记无虞；不等则首装前
  必须先处理容量变体）。

## 二、经典蓝牙 BR/EDR：他机无法发现、无法建 ACL

用户自述"BR/EDR 接收路径部分正常，但 Inquiry/Page Response 响应链路异常"。
注：他的措辞从内核侧看是反的——平板作为扫描者能收到他机的响应 = 平板侧
RX；缺失的是平板被扫描/被寻呼时的**响应 TX**。

### 链路现状（6.17 产品线，结构完整）

- 电源：`wcn6855-pmu` 节点 `bt-enable-gpios = <&tlmm 81>`（与原厂 FDT
  逐线一致，注释在板级 DTS:383-389）；provider 是 pwrseq-qcom-wcn，被
  强制内建（`device/configs/liuqin-firstboot.config:329-330`）。
- 传输：`&uart20`（QUPv3 wrapper2 SE6）+ 子节点
  `compatible = "qcom,wcn6855-bt"` + 8 路供电（板级 DTS，引脚逐线对照
  原厂）。`hci_qca` of_match 表命中。
- 固件：rampatch `qca/hpbtfw%02x.tlv`、NVM `qca/hpnv<rom>[g][.b<bid>]`
  （`btqca.c:749-767`），固件池从 stock `BTFM.bin` 提取**全构造名集**
  （95 文件，哈希钉死，`tools/build-liuqin-firmware-prep.sh:45-52`），
  且 initramfs 与 rootfs 各备一份（`request_firmware` 在 initramfs 阶段
  就触发，`build-initramfs.sh:36-44`）。
- 地址：装机时只读挂载 persist，**缺失 `.bt_nv.bin` 即安装失败**
  （`install-root.sh:215-221`）；`provision.sh` 转
  `/var/lib/liuqin-private/bluetooth-address`；开机后
  `liuqin-bt-preconfigure.service` → `liuqin-bt-public-addr` 用 btmgmt 把
  地址写入 unconfigured MGMT index，`bluetooth.service` 通过 drop-in
  `Requires=` 该单元。BlueZ 侧设置 `AutoEnable=true`（`build-liuqin-native-root.sh:160-186`）。
- `qca_setup()` 对该芯片设 `HCI_QUIRK_SIMULTANEOUS_DISCOVERY`。

### 分诊排序（平凡假设优先）

1. **unconfigured/BDADDR 用户态链失败（首要）**：芯片以 NVM 占位地址
   `00:00:00:00:5A:AD` 上电，靠 `liuqin-bt-public-addr` 配置后 BlueZ 才接
   管。该单元失败 → `bluetooth.service` 起不来（Requires=）→ 无适配器 →
   iscan/pscan 从未设置 → 他机既不能发现也不能寻呼平板，而平板自己仍能
   收到他机的响应。具体失败点：provisioned 地址缺失/为占位值、早期
   btmgmt 竞态（该路被反复咬过，helper 里有 2 秒请求封顶与 90 秒单元
   超时的注释）、btmgmt 缺失。
2. **BlueZ 扫描设置（次之）**：BlueZ 默认 Discoverable 关，GNOME 不打开
   BT 面板就不可被发现；pscan 需 Connectable 开且 rfkill 未 block。
3. **NVM 未加载（回退）**：`-ENOENT`/`-EAGAIN` 被驱动容忍并进入 ROM-FW
   模式（`hci_qca.c` 的 `QCA_ROM_FW` 分支），BR/EDR 未校准但芯片仍枚举
   ——"RX 部分正常、TX 响应始终不对"的一个可能生成器。触发条件是
   `/usr/lib/firmware/qca/` 缺失或 initramfs 没带该集合。
4. **使能脚指错 PMIC（排除）**：bt-en 是 TLMM gpio81，与原厂一致；共享
   PMU 的 WLAN 已工作（pwrseq 链被证明）。
5. **SAR/发射功率限幅（排除）**：树内无 SAR 框架、无 TX 功率钳制代码。

**判别性最强的单条数据：同一次安装上 LE 是否正常**。LE 广播/配对可用
（项目唯一显式验证过的路径就是 LE HoG 键盘）⇒ 射频 TX 链路基本排除，
指向 BlueZ 适配器模式 / NVM 的 BR/EDR 段 / SIMULTANEOUS_DISCOVERY 交互；
LE 也坏 ⇒ 适配器根本没起来或多半跑在无 NVM 的 ROM-FW 上，先查
preconfigure 单元。

### 诊断清单（按顺序）

0. `systemctl status liuqin-bt-preconfigure.service bluetooth.service` +
   `journalctl -b -u liuqin-bt-preconfigure.service`（helper 成功打
   "configured with the provisioned public address"，失败按 `die()` 原
   文指认模式）。
1. `ls -l /var/lib/liuqin-private/` + 地址文件（0600 root:root、18 字节、
   合法 MAC、≠ 00:00:00:00:5A:AD）。
2. `dmesg | grep -iE 'bluetooth|hci|qca'`（应有 `setting up wcn6855`、
   `QCA setup on UART is completed`；出现
   `QCA Failed to request file: qca/hpnv20.bin (-2)` 类行 ⇒ 第 3 假设）。
3. `ls /usr/lib/firmware/qca/`（hpbtfw2x.tlv + hpnv2x 全 .b<bid> 集在位）。
4. `btmgmt info`：index 0 应为 Primary controller、addr = provisioned
   地址、current settings 含 powered connectable；残留 Unconfigured 条
   目或占位地址 ⇒ 假设 1/2 成立。
5. `hciconfig -a hci0`（或 btmgmt）：`ISCAN PSCAN` 标志与 RX/TX 字节
   计数——他机寻呼后 RX 涨 TX 不涨 = "听见但从不响应"。
6. `rfkill list bluetooth` + `bluetoothctl show`（Powered/Discoverable/
   Connectable 状态）。
7. `btmgmt config`（残留 unconfigured index）。
8. **LE 测（先于任何射频归因）**：`bluetoothctl` 扫描 / 配对 LE 键盘。
9. 他机扫描/寻呼的同时 `btmon` 抓包，看控制器是否上报入站 inquiry/page
   以及是否有任何 TX。
10. 仍未定位：`cat /sys/kernel/debug/bluetooth/hci0/fw_version`。

### 对 7.0 移植的影响

- "7.0 板级 DTS 可能没有 BT 节点"为**假**：`liuqin-7.0` 板级 DTS 有完整
  `&uart20` + `bluetooth`（`qcom,wcn6855-bt`）与 `wcn6855-pmu`，驱动
  of_match 命中。
- 7.0 特有的差异：`btqca.c` 把 WCN6855 的**主**请求名改成带 `wcn` 前缀
  （`qca/wcnhpbtfw%02x.tlv` / `qca/wcnhpnv<rom>…`，上游注释"historical
  reasons… now corrected"），**任何 `err < 0`** 都会回退到老命名
  （`btqca.c` 回退分支）。现有固件集没有 `wcn*` 文件——靠回退仍然能
  加载，dmesg 会先出现一条主名请求失败再出现老名成功。功能无碍，但若
  哪次改动动了回退语义就会静默断链：BT bring-up 时把这一点写进验收点。
- 用户态半边（persist provisioning → preconfigure → bluetooth.service）
  是 rootfs 层、内核无关，7.0 把 hci0 带起来后原样复用。
- BT 在 7.0 仍是 TD5 的 P1/P2 延后项；bring-up 起步时按上面清单 0-4 执行。
